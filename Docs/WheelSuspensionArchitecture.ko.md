# DriveTest 휠 & 서스펜션 아키텍처

> 이 문서는 `Docs/WheelSuspensionArchitecture.md`의 한국어판이다.
> 영어 원문을 **아키텍처의 기준 문서(source of truth)**로 유지하며, 이 문서는 이해를 돕기 위한 동기화된 한국어판이다.
> 작업 번호와 체크 상태는 영어 원문과 동일하게 유지한다.

## 1. 목적

현재 휠/서스펜션 구현을 기계적으로 일관된 키네마틱 서스펜션 구조로 교체한다. 첫 구체 구조로 Double Wishbone과 MacPherson을 사용하며, 공통 추상화는 두 구조가 검증된 뒤 결정한다.

이 작업은 기존 `Wheel::Update()` 구현에 기능을 덧붙이는 것이 아니라 아키텍처를 교체하는 작업이다.

## 2. 좌표계 규약

- 전방 = +Z
- 위 = +Y
- 오른쪽 = -X
- 왼쪽 = +X

이 좌표계는 서스펜션 교체 과정에서도 변경하지 않는다.

### 2.1 차량 로컬 기준축과 하중 이동 부호 규약

위 좌표계는 **차량 로컬 좌표계**다. 월드 좌표계가 아니며, 휠마다 별도의 좌표계 규약을 사용하지 않는다.

```text
                 +Y 위
                  ↑
                  │
       +X 좌  ←  ●  →  -X 우
                  │
                  └────────→ +Z 전방
```

- `+X` = 차량의 왼쪽
- `-X` = 차량의 오른쪽
- `+Y` = 위
- `+Z` = 전방
- 차체가 회전하면 이 축들도 차체와 함께 월드 공간으로 회전한다.
- `Wheel::GetWorldOrientation()`은 이 차량 로컬 허브 좌표계를 월드 공간으로 변환하는 회전이다.
- 실제 quaternion basis에는 `+X = left`를 사용한다. `-X = right`는 그 반대 방향으로 파생한다.

코너링 진단에서 하중 이동의 부호는 다음과 같이 고정한다.

```text
양의 steering 입력  → 우회전 → 횡가속도는 -X 방향
                   → 좌측/바깥쪽 하중 증가
                   → leftLoad - rightLoad > 0

음의 steering 입력  → 좌회전 → 횡가속도는 +X 방향
                   → 우측/바깥쪽 하중 증가
                   → leftLoad - rightLoad < 0
```

의도한 물리 전달 경로는 다음과 같다.

```text
접촉점에서 발생한 타이어 횡력
            ↓
       차체 롤 토크
            ↓
          차체 롤
            ↓
 좌/우 휠 기하 + 레이 거리 차이
            ↓
 좌/우 서스펜션 압축량 차이
            ↓
 좌/우 스프링 정상하중 차이
```

따라서 하중 이동 검증은 스프링 레이트, steering scale, 테스트 임계값 등을 바꿔서 결과를 맞추는 방식이 아니라 이 전달 경로 자체가 살아 있는지를 검증해야 한다.

## 3. 설계 원칙

- [x] 각 휠을 차체에 직접 붙은 점이 아니라 실제 서스펜션 어셈블리의 일부로 모델링한다.
- [x] 서스펜션 키네마틱스, 스티어링 기하, 휠/허브 상태, 타이어 접촉, 타이어 힘 계산을 분리한다.
- [ ] 호환성을 위해 기존 `Wheel` 구현을 보존하지 않는다.
- [ ] 컨트롤 암을 독립적인 강체로 풀지 않고 키네마틱 링크/제약으로 취급한다.
- [ ] 휠의 움직임은 서스펜션 기하가 결정해야 한다.
- [ ] 타이어 힘은 임의의 휠 마운트가 아니라 타이어 접촉점에 적용한다.
- [ ] 불가능한 서스펜션 상태를 통해 지면 접촉이 차체를 아래로 끌어당기거나 붙잡지 않도록 한다.

## 4. 서스펜션 아키텍처

### 4.1 Double Wishbone

각 휠 코너는 개념적으로 다음과 같다.

```text
차체
 ├── 상부 컨트롤 암 ──┐
 │                    │
 └── 하부 컨트롤 암 ──┤── 너클/업라이트 ── 허브 ── 휠/타이어
                      │
                 스프링/댐퍼
```

상·하부 암이 업라이트/허브 위치를 구속한다.

- [ ] 상부 암 차체 피벗 정의
- [ ] 상부 외측 조인트 정의
- [ ] 하부 암 차체 피벗 정의
- [ ] 하부 외측 조인트 정의
- [ ] 암 기하로부터 업라이트/허브 위치 계산
- [ ] 중복 특수 로직 대신 설정을 통해 좌우 대칭 유지

### 4.2 서스펜션 축

서스펜션 스트로크는 실제 서스펜션 기하에서 나와야 한다.

- [ ] 고정된 월드 다운 방향으로 서스펜션 스트로크를 정의하지 않는다.
- [ ] 차체 장착점에서 `direction * suspensionLength`를 더하는 방식으로 휠 이동을 만들지 않는다.
- [ ] 스프링/댐퍼 장착점을 명시적으로 정의한다.
- [ ] 두 장착점으로부터 스프링/댐퍼 축을 계산한다.
- [ ] 두 장착점 사이 거리로 스프링/댐퍼 길이를 계산한다.
- [ ] 서스펜션 스트로크 제한과 댐핑 힘을 분리한다.

### 4.3 업라이트 / 허브

업라이트는 상·하부 컨트롤 암, 스티어링 장치, 휠 허브를 연결한다.

- [ ] 서스펜션 키네마틱스로 허브 위치를 정의한다.
- [ ] 서스펜션과 스티어링 기하로 허브 방향을 정의한다.
- [ ] 휠의 시각적 변환은 허브 상태에서 파생한다.

### 4.4 스프링 / 댐퍼

스프링/댐퍼 동작은 서스펜션 기하와 분리한다.

- [ ] 정적 길이 정의
- [ ] 범프 스트로크 / 최소 허용 길이 정의
- [ ] 리바운드 스트로크 / 최대 허용 길이 정의
- [ ] 압축 댐핑 정의
- [ ] 리바운드 댐핑 정의
- [ ] 서스펜션 길이를 기계적 한계로 제한
- [ ] 댐핑으로 기계적 스트로크 제한을 대신하지 않는다.
- [ ] 접지된 휠이 잘못된 서스펜션 상태로 전복된 차체를 지면 쪽으로 끌어당기지 않도록 한다.

## 5. 스티어링 아키텍처

앞바퀴 스티어링은 월드/로컬 Y축을 중심으로 휠만 제자리 회전시키는 것이 아니라, 스티어링 너클/업라이트를 실제 스티어링 축을 중심으로 회전시킨다.

### 5.1 스티어링 축

스티어링 축은 현재 서스펜션 자세에서 얻어지는 기하 결과다.

- [ ] 상·하부 스티어링 축 점 정의
- [ ] 두 점으로부터 스티어링 축 계산
- [ ] 해당 축을 중심으로 업라이트/허브 회전
- [ ] 고정된 월드 Y축을 사용하지 않는다.

### 5.2 스티어링 기하

스티어링 기하는 다음을 지원해야 한다.

- [ ] 캐스터(Caster)
- [ ] KPI / SAI
- [ ] 스크럽 반경(Scrub radius)
- [ ] 스티어링 암 기하
- [ ] 애커먼(Ackermann) 스티어링 관계

스티어링 축이 기울어져 있거나 오프셋되어 있다면 회전에 따라 허브 위치도 함께 변할 수 있어야 한다.

## 6. 휠 & 타이어 아키텍처

개념적인 업데이트 흐름:

```text
Double Wishbone
      ↓
업라이트 / 허브
      ↓
휠
      ↓
타이어
      ↓
접촉 패치
      ↓
타이어 힘
```

### 서스펜션

- [x] 휠/허브 키네마틱스를 결정한다.
- [ ] 서스펜션 압축량과 속도를 결정한다.
- [ ] 스프링/댐퍼 힘을 생성한다.

### 스티어링

- [ ] 스티어링 축 방향을 결정한다.
- [ ] 스티어링에 따른 허브/휠 변환을 결정한다.

### 휠 / 허브

- [ ] 휠 회전 상태를 저장한다.
- [ ] 타이어 계산과 렌더링에 휠 중심/방향을 제공한다.
- [ ] 물리 허브 상태에서 시각적 휠 변환을 파생한다.

### 타이어

- [ ] 지면 접촉을 결정한다.
- [ ] 접촉점 속도를 결정한다.
- [ ] 종방향/횡방향 타이어 힘을 계산한다.
- [ ] 접촉 패치에 타이어 힘을 적용한다.
- [ ] 내부 서스펜션 구현과 독립적으로 유지한다.

## 7. 서스펜션 키네마틱스

서스펜션은 독립 강체들의 집합이 아니라 주로 키네마틱 구조다.

- [ ] 매 물리 업데이트마다 컨트롤 암 기하를 계산한다.
- [ ] 계산된 업라이트 위치에서 휠 중심을 얻는다.
- [ ] 업라이트 방향에서 캠버를 얻는다.
- [ ] 서스펜션 스트로크에 따른 트랙 폭 변화를 기하가 자연스럽게 만든다.
- [ ] 기하가 원인일 경우 휠베이스 변화도 자연스럽게 만든다.
- [ ] 서스펜션 기하가 캐스터/캠버 변화를 결정하도록 하며 휠을 사후 수동 보정하지 않는다.

## 8. 차량 물리 업데이트 순서

```text
차체 변환
    ↓
서스펜션 기하 계산
    ↓
업라이트 / 허브 변환
    ↓
스티어링 기하
    ↓
휠 중심 + 방향
    ↓
지면 접촉
    ↓
서스펜션 압축량
    ↓
스프링 / 댐퍼 힘
    ↓
타이어 접촉점 속도
    ↓
타이어 힘
    ↓
차체에 힘 적용
    ↓
RigidBody 적분
```

- [ ] 새 클래스들이 완성되면 최종 구체적 업데이트 순서를 구현하고 문서화한다.

#### 4-2 — Tire 접촉 패치 / 힘 기준 이전

**목표:** 타이어 접촉 좌표계를 solved wheel hub orientation에서 직접 얻도록 이전하면서, 기존 타이어 힘 모델 자체는 보존한다.

책임 경계는 다음과 같다.

```
Suspension Geometry
        ↓
   Hub Position
   Hub Orientation
        ↓
       Wheel
        ↓
 Contact Point + Normal
        ↓
 접촉면에 hub forward 투영
        ↓
 Tire contact basis
   ├─ forward
   └─ lateral
        ↓
 기존 slip / grip / force 모델
```

**중요한 좌표계 사항:** DriveTest의 차량 오른쪽은 `-X`이지만 quaternion 회전 basis는 오른손 좌표계다. 따라서 hub orientation은 물리적인 `+X = left`, `+Y = up`, `+Z = forward` 축으로 구성해야 한다. 차량 오른쪽(`-X`)을 quaternion basis 축으로 직접 사용하면 회전이 아니라 반사(reflection)가 된다.

**Tire state basis:**

- `forward = hubOrientation * VehicleCoordinates::Forward()`.
- contact normal을 사용해 `forward`를 접촉면에 투영한다.
- 투영된 forward를 정규화한다.
- `lateral = forward × contactNormal`로 계산하며, 평탄한 도로에서는 차량 오른쪽(`-X`)이 된다.
- solved hub orientation을 사용한 뒤에는 `Wheel::GetSteeringAngle()`을 다시 적용하지 않는다. 스티어링은 이미 hub orientation에 반영되어 있다.

**힘 모델 경계:**

- 기존 slip ratio 계산을 유지한다.
- 기존 slip angle 계산을 유지한다.
- 기존 grip curve를 유지한다.
- 기존 friction limit 및 combined-slip scaling을 유지한다.
- rolling resistance 동작을 유지한다.
- 접촉점 속도를 해석하고 결과 힘을 적용하는 좌표 basis만 이전한다.

**검증:**

- [x] 차량 좌표계에서 hub orientation이 올바른 quaternion 회전이 되도록 basis 수정.
- [x] solved hub orientation으로 Tire 접촉 forward/lateral basis 계산.
- [x] steering이 두 번 적용되지 않도록 제거.
- [x] Tire basis와 projected solved hub basis를 비교하는 독립 진단 추가.
- [x] 이전 후 Linux 전체 빌드 및 vehicle diagnostics 실행.

**현재 상태:** solved hub 기반 Tire 접촉 기준 이전은 완료됐다. 사용자가 Linux 빌드와 등록된 ctest 두 항목(PhysicsDiagnostics, VehicleDiagnostics)이 모두 통과한 것을 확인했다. 이는 현재 회귀 테스트 통과를 뜻하며, 경사면/모서리/점프 착지의 접촉 탐색까지 검증했다는 뜻은 아니다. 해당 항목은 Phase 4-3에서 별도로 다룬다.

### Phase 4-3 — 교체 가능한 Wheel Contact 아키텍처

**목표:** 휠과 지면의 접촉을 탐색하는 방식을 영구적인 설계 선택으로 고정하지 않고, 구현체만 교체할 수 있게 한다. Raycast는 여러 후보 중 하나일 뿐이며 인터페이스의 기준이 되어서는 안 된다.

이 작업 단위는 아키텍처 명세다. 최종 접촉 알고리즘을 선택하지 않으며, 런타임 코드가 이미 분리됐다고 주장하지 않는다.

#### 반드시 지킬 설계 목표

개발자가 새 접촉 알고리즘을 발견하더라도 `Wheel`, `Suspension`, `Tire` 또는 차량 힘 계산 코드를 수정하지 않고 추가·선택할 수 있어야 한다. 알고리즘별 코드는 하나의 안정적인 제공자(provider) 경계 뒤에 둔다. 결과를 소비하는 코드는 결과 계약에만 의존한다.

후보 제공자는 다음을 포함하지만 여기에 한정되지 않으며, 현재 우선순위나 채택 결정을 뜻하지 않는다.

- 단일 Ray / 방향을 개선한 Ray.
- 다중 Ray 또는 그 밖의 이산 샘플링.
- Sphere Cast, Shape Cast 또는 스윕 볼륨.
- 타이어 형상 기반 또는 다중 접촉점 기하 모델.
- 합의된 계약에 맞게 어댑터를 제공할 수 있는 노드/빔 기반 또는 미래의 타이어 접촉 구현.
- 지금 목록에 없는 모든 미래 알고리즘.

목록은 의도적으로 열어 둔다. 소비자 코드에 `if (isRaycast)` 같은 알고리즘별 분기를 추가하지 않는다.

#### 목표 의존성 구조

```text
Vehicle / Car 조립 지점
    └── IWheelContactProvider 하나를 선택·주입
                  |
                  v
          휠 기하 + 일반 쿼리 입력
                  |
                  v
       IWheelContactProvider
       ├── Raycast 제공자
       ├── 다중 샘플 제공자
       ├── Shape/Sweep 제공자
       └── 미래의 사용자 정의 제공자
                  |
                  v
          WheelContactResult
                  |
          ┌───────┴────────┐
          v                v
     Suspension           Tire
   서스펜션 기하/상태    접촉점/법선/
   기반 스프링 길이     표면/속도 소비
                          /
                         /
             차량 힘 통합
```

이 그림은 목표 의존성 방향이며 현재 구현 상태가 아니다. 구체 제공자 선택은 차량/애플리케이션 조립 지점 또는 설정에서 담당한다. `Wheel`, `Suspension`, `Tire`는 구체 제공자를 직접 생성하거나 선택하거나 식별하면 안 된다.

#### 인터페이스와 데이터 계약

구현 시 제공자 중립적인 인터페이스를 도입한다. 아래 이름과 시그니처는 개념을 설명하기 위한 예시이며, 코드 API 검토 전까지 고정하지 않는다.

```cpp
class IWheelContactProvider {
public:
    virtual ~IWheelContactProvider() = default;
    virtual WheelContactResult Query(
        const WheelContactInput& input,
        const PhysicsWorld& physicsWorld,
        const RigidBody* ignoredBody
    ) const = 0;
};
```

위 인터페이스는 첫 구현의 실제 API와 일치한다. 제공자는 읽기 전용 `PhysicsWorld` 쿼리 컨텍스트와 충돌 제외 대상을 받는다. `Wheel`은 이 컨텍스트를 전달만 하고 구체 쿼리를 직접 호출하지 않는다. 별도 월드 어댑터는 대체 제공자가 실제로 필요한 기능을 현재 API에서 얻을 수 없다는 근거가 생길 때까지 보류한다. 그때도 차량 소비자에 알고리즘별 분기를 추가하지 말고 이 경계에 기능을 추가한다.

계약은 다음을 만족해야 한다.

- **일반화된 입력:** 휠/허브 위치와 방향, 필요한 타이어 치수·형상 설명, 충돌 필터, 알고리즘 중립적인 탐색 범위/설정. Ray, Ray 방향, Ray hit distance를 보편 입력 모델로 삼지 않는다.
- **안정된 결과:** 명시적인 접촉 상태, 0개 이상의 접촉 샘플, 각 샘플의 월드 공간 접촉점과 그에 대응하는 법선, 가능한 경우 표면/재질 식별자, 원래 쿼리가 제공할 수 있는 경우 선택적 간격/관통량 또는 충돌 특징 메타데이터.
- **명시적인 기능 차이:** 어떤 전략이 특정 필드를 제공할 수 없다면 값을 지어내거나 의미를 몰래 바꾸지 말고, 해당 정보의 미지원/부재를 명시한다. 소비자는 구체 알고리즘 타입에 따라 분기하지 않는다.
- **일관된 의미:** 접촉점, 법선, 표면 식별자, 선택적 거리/관통 데이터가 동일한 접촉 샘플을 설명해야 한다. 좌표 공간, 법선 방향, 단위, 유효성, 순서, 빈 결과의 의미를 정의한다.
- **다중 접촉:** 첫 제공자가 하나의 샘플만 반환하더라도 결과 타입 자체는 여러 샘플을 표현할 수 있어야 한다. 인터페이스 경계에서 모든 전략의 결과를 임의의 점 하나로 강제 축약하지 않는다.
- **소유권과 수명:** 결과 데이터는 임시 쿼리 버퍼나 제공자 내부 메모리가 사라져도 유효해야 한다.
- **힘 모델 은닉:** 제공자는 접촉을 탐색하고 설명한다. 타이어 힘 계산과 차체 힘 적용은 별도 책임으로 유지한다. 향후 아키텍처 검토에서 명시적으로 바꾸지 않는 한 이 경계를 합치지 않는다.

공개된 휠/타이어 접촉 계약에 `RaycastResult`, Ray 파라미터, 특정 cast 핸들, 제공자 전용 버퍼 같은 구현 종속 타입을 노출하지 않는다. 현재 Raycast 제공자는 접촉 샘플 하나를 반환하고, `Wheel`은 전체 결과를 보관하지만 기존 타이어 힘 계산 경로는 아직 첫 샘플만 소비한다. 다중 접촉점 힘 합산은 미구현이다. 현재 서스펜션 길이도 실제 스프링 장착점 길이가 아니라 허브와 접촉점 사이의 임시 기하 추정값이므로, 이 분리는 별도 미완료 작업이다.

#### 책임 경계

- **접촉 제공자:** 접촉을 탐색하고 제공자별 후보 필터링/선택을 담당한다. Ray/shape/sample 세부사항과 알고리즘별 허용오차를 소유한다.
- **접촉 쿼리 월드 접근:** 현재 제공자는 읽기 전용 `PhysicsWorld`를 쿼리 컨텍스트로 받는다. `Wheel`은 이를 전달할 뿐 Raycast를 직접 호출하거나 충돌 형상을 검사하지 않는다. 대체 제공자에 필요한 월드 기능이 없다면 중립 어댑터 또는 물리 월드 API를 통해 이 경계에 추가하고, `Wheel`, `Suspension`, `Tire`에 구현 세부사항을 노출하지 않는다.
- **Wheel / 허브:** 휠 회전 상태를 소유하고 안정된 API로 접촉 결과를 제공한다. 지면 탐색 로직을 직접 구현하지 않는다.
- **Suspension Geometry:** 허브 위치/방향과 실제 스프링·댐퍼 장착점 위치를 계산한다.
- **Suspension 모델:** 실제 스프링·댐퍼 장착점으로 스프링 길이를 계산하고, 자체 기하/상태에서 압축량·속도·스프링/댐퍼 힘을 계산한다. 접촉 거리로 스프링 길이를 추정하지 않는다.
- **Tire:** 접촉 상태/샘플, 휠/허브 상태, 접촉점 속도, 표면 정보를 소비해 타이어 상태와 힘을 계산한다. 지면을 직접 쿼리하지 않고, 어떤 제공자가 결과를 만들었는지도 알지 못한다.
- **Car / 차량 통합:** 제공자를 주입하고 업데이트 순서를 조율하며 서스펜션과 타이어 힘을 적절한 기계적 적용점에 적용한다. 알고리즘별 로직을 갖지 않는다.
- **진단:** 소비자 코드가 활성 제공자를 알 필요 없이 제공자 계약과 차량 동작을 테스트한다.

#### 교체 가능성 검증 기준

인터페이스가 존재한다는 사실만으로 아키텍처가 완성된 것은 아니다. 다음의 실용적인 검증을 통과해야 한다.

1. 새로운 제공자를 별도의 구현 파일로 추가한다.
2. 조립 지점/설정에서 새 제공자를 등록하거나 선택한다.
3. 기존 제공자와 새 제공자를 동일한 소비자 수준 테스트에서 실행한다.
4. `Wheel`, `Suspension`, `Tire`, 이들의 공개 소비자 API, 힘 모델 코드에 알고리즘별 수정이 필요하지 않은지 확인한다.

새 제공자를 추가할 때 `Wheel`, `Suspension`, `Tire`를 수정해야 한다면 경계로 구현 세부사항이 새어 나온 것이다. 알고리즘을 더 추가하기 전에 경계를 재설계한다.

현실적인 한계도 명시한다. 제공자가 완전히 교체 가능한 구현체가 되려면 엔진이 해당 알고리즘에 필요한 월드 데이터와 연산을 제공해야 한다. 새로운 방식에 기존에 없는 충돌 월드 기능이 필요하면 월드 어댑터 뒤에 그 기능을 추가한다. 새로운 알고리즘을 휠/서스펜션/타이어 소비자 코드에 밀어 넣지 않는다. 노드/빔 기반의 변형 타이어처럼 동역학 상태 자체가 달라지는 모델은 단순한 접촉점 탐색 교체를 넘어설 수 있으므로 별도의 모델 수준 설계가 필요할 수 있다. 그렇다고 일반 접촉 제공자를 소비자에 결합해야 하는 것은 아니다.

#### 서스펜션 및 타이어 불변 조건

- 월드 아래 방향 단일 Ray는 휠-지면 접촉의 정의가 아니다.
- 접촉 탐색이 서스펜션 기구학을 결정하지 않는다.
- 스프링/댐퍼 길이는 실제 기하의 장착점으로 계산하며, Ray hit distance나 제공자별 거리로 계산하지 않는다.
- 기하학적으로 접촉 중이어도 normal load는 0일 수 있다. 유효한 접촉 기하/기준축은 보존하되 타이어 힘을 만들어내지 않는다.
- 유효한 접촉이 없으면 지면에서 유래한 타이어 힘도 없어야 한다.
- 접촉 샘플의 점/법선 짝을 일관되게 유지하고, 결과 힘은 의도된 접촉 위치에 적용한다. 여러 샘플을 합산한다면 힘과 토크가 어떻게 보존되는지 문서화한다.
- 차량 좌표 규약을 유지한다: +X 왼쪽, -X 오른쪽, +Y 위, +Z 전방.
- 접촉 오류를 스프링 레이트, 조향 부호/크기, 마찰 계수 또는 테스트 임계값 변경으로 감추지 않는다.
- 제공자 교체로 단위, 좌표 공간, 접촉 상태 의미, 법선 방향이 조용히 바뀌면 안 된다.

#### 탐색 전략 결정은 의도적으로 보류

이름, 평판 또는 근거 없는 정확도 가정으로 알고리즘을 선택하지 않는다. 경계와 기존 월드 쿼리 기능을 조사한 뒤 같은 테스트를 사용해 후보를 비교한다. 경사, 뱅크, 마루, 골, 삼각형 경계, 모서리, 휠 리프트, 점프 착지의 정확성뿐 아니라 안정성, 결정성, 성능, 구현 비용도 비교한다.

리팩터링 기준선을 보존하기 위해 기존 Raycast를 첫 번째 어댑터로 남길 수 있다. 그렇다고 Raycast를 장기적으로 선호한다는 뜻은 아니며, 그 의미를 계약에 새겨도 된다는 뜻도 아니다.

#### 구현 순서

1. **기존 API 조사:** 지형, 도로, 형상 충돌, `PhysicsWorld`, 현재 `Wheel::Update()`의 쿼리/힘 계산 경로를 조사한다.
2. **계약 명세:** 입력, 결과, 접촉 상태 의미, 다중 샘플, 선택적 기능, 좌표 공간, 단위, 빈 결과 동작을 정의한다.
3. **경계 도입:** 타이어 그립 동작을 바꾸지 않고 제공자 인터페이스와 중립적인 접촉 결과를 추가한다. 대체 제공자가 현재 `PhysicsWorld` API에 없는 기능을 실제로 요구할 때까지 별도 월드 어댑터는 보류한다.
4. **현재 쿼리 감싸기:** 기존 동작을 인터페이스 뒤의 한 제공자로 옮긴다. 정확성에 필수인 경우가 아니라면 같은 작업에서 탐색 알고리즘까지 개선하지 않는다.
5. **제공자 주입:** `Wheel`, `Suspension`, `Tire` 바깥에서 구현체를 선택하고, 소비자에서 구체 쿼리 생성과 알고리즘 판별을 제거한다.
6. **서스펜션 분리:** 실제 서스펜션 기하/장착점 계산을 런타임 경로에 연결하고, 레이 거리와 스프링 길이의 기존 결합을 제거한다.
7. **계약 테스트:** 결정론적 가짜 제공자로 접촉 없음, 단일 접촉, 다중 접촉, 법선 변화, 선택적 데이터 부재를 테스트한다.
8. **장면 진단:** 평지 및 좌우 대칭, 경사와 뱅크, 마루/골, 지형·도로 모서리와 삼각형 경계, 앞바퀴 우선 경사 착지, 일부 휠 공중 상태, 접촉점/법선 짝, 힘 적용점과 차체 토크를 검증한다.
9. **제공자 비교:** 동일한 테스트 하네스가 준비된 후에만 대안 구현을 추가하고 비교한다. 제공자는 별도 파일에 두고 소비자 수정 없이 선택 가능해야 한다.

각 구현 작업 단위는 수정 전 정확한 파일 목록을 명시하고, 검증 증거를 확보한 뒤에만 체크리스트를 완료 처리하며, 필수 엔지니어링/검증 스킬을 따라야 한다.

- [x] 로컬 빌드 및 진단 실행 통과(사용자 실행 결과).

실행 결과: `invalidConfigRejected=1`이며 기존 MacPherson 진단 항목도 모두 `1`, 프로그램은 `[PASS] MacPherson travel diagnostics`를 출력했다(사용자 실행 결과). 스트로크 경계 수치는 합성 설정의 진단값이며 실제 차량의 스트로크 한계를 뜻하지 않는다.

자동 스트럿 길이는 기존 동작대로 설정된 상부 마운트와 하부 마운트(`outerJoint + lowerMountOffset`) 사이의 거리로 계산한다. 양수는 명시적 길이로 취급한다. 이번 작업은 설정값 유효성을 검사하지만 모든 스트로크에서 기하학적 해가 존재함을 보장하지는 않는다. 잘못된 유한성/음수 길이 설정이 기존 설정을 대체하지 않고 거부되면 진단에 `invalidConfigRejected=1`이 표시된다.

### Phase 7-1 — 서스펜션 기하 소비자 인터페이스

- [x] `ISuspensionGeometry`에 스트로크 솔브, 허브 변환, 스프링 마운트, 스티어링 축, 스티어링 적용 계약을 정의.
- [x] `DoubleWishbone`과 `MacPherson`이 같은 기하 인터페이스를 구현.
- [x] `Wheel`이 구체적인 `DoubleWishbone` 대신 인터페이스에 의존하도록 변경.
- [x] 앱 및 차량 진단 빌드 대상에 `MacPherson.cpp` 포함.
- [x] Linux 앱 및 진단 타깃 컴파일 확인(사용자 실행 결과: `DriveTest` 빌드 성공).
- [x] `VehicleDiagnostics`, Physics, MacPherson, Suspension 진단 통과 확인(사용자 실행 결과).
- [ ] `DoubleWishboneDiagnostics`는 별도 조사 대상으로 보류한다. 현재 `hubPosition` 검사에서 실패하며 이번 작업 범위에서는 수정하지 않는다.
- [ ] `Car`의 구체 기하 배열 및 설정 생성 경로를 교체 가능한 런타임 구성으로 전환.

**검증 근거(사용자 실행 결과):** Linux 빌드 후 CTest에서 `PhysicsDiagnostics`, `VehicleDiagnostics`, `MacPhersonDiagnostics`, `SuspensionDiagnostics`가 통과했다. `DoubleWishboneDiagnostics`는 `hubPosition=0`으로 실패했다. 이 테스트는 원인 조사 전까지 CTest에서 임시 비활성화했으며, 실행 파일 빌드는 유지된다. 따라서 전체 진단이 통과한 것은 아니다.

`Car` 의존성 조사 결과: `Car.h`가 `DoubleWishbone.h`를 직접 포함하고 배열 및 getter를 구체 타입으로 노출한다. `Car.cpp`도 `DoubleWishboneConfig` 구성, `Configure`/`Solve`, 복사 후보를 이용한 스트로크 탐색, `ApplySteering`에 직접 의존한다. 현재 `VehicleConfig`에는 Double Wishbone 파라미터만 있으므로, `ISuspensionGeometry`를 배열 타입으로 바꾸는 것만으로는 MacPherson 런타임 선택이 가능해지지 않는다. 다음 작업은 기하 구현 선택/생성과 설정 데이터의 경계를 설계한 뒤 Car 업데이트 경로를 일반화하는 것이다.

이 변경은 소비자 경계를 정하는 첫 단계이며, 아직 `Car`에서 MacPherson을 선택하거나 실행할 수 있게 만든 것은 아니다. `Wheel`은 더 이상 구체 서스펜션 클래스를 직접 참조하지 않지만, 여전히 기하 인터페이스와 서스펜션 모델을 함께 받는다. 또한 `Car`는 구체 `DoubleWishbone` 배열과 해당 기하에 특화된 스트로크 탐색을 소유한다. 런타임 교체는 별도의 다음 작업이다.

## 13. 비목표

첫 구현에서는 다음을 요구하지 않는다.

- 독립 강체로 시뮬레이션하는 컨트롤 암
- 완전한 멀티바디 동역학 솔버
- 유압식 스티어링 시뮬레이션
- 부싱 탄성의 상세 모델
- 댐퍼 밸브/온도 모델
- 제조 수준의 서스펜션 모델링

첫 목표는 DriveTest의 기존 rigid-body/타이어 물리와 깔끔하게 연결되는 안정적이고 기계적으로 일관된 키네마틱 Double Wishbone 시스템이다.
