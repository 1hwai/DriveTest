# 휠·서스펜션 복구 작업 계획

> 이 문서는 현재 구현을 감사하고 바로잡기 위한 후속 작업 흐름이다. 기존 `Docs/WheelSuspensionArchitecture.md`의 작업 이력을 대체하거나 번호를 다시 매기지 않는다.
>
> 기존 아키텍처 문서는 설계 기준으로 유지한다. 이 계획은 실제 코드가 무엇을 하는지 확인하고, 설계와의 차이를 기록하며, 목표에 도달하기 위한 작업을 정의한다.
>
> 이 문서와 `Docs/WheelSuspensionRecoveryPlan.md`를 동기화한다. 근거에 기반한 조사 결과와 합의된 해결책은 대응하는 `.solution.md` 문서에 기록한다.

## 이 작업 흐름이 필요한 이유

기존 `1-1`부터 `4-2`까지의 작업은 기하 구조, 서스펜션, 조향, 타이어 통합의 방향을 정했다. 그러나 클래스가 존재하거나 함수 호출 경로가 있다는 사실만으로 기계 모델이 정확하거나 런타임이 결과를 일관되게 사용한다고 증명할 수는 없다.

원인을 미리 단정하지 않고 다음 질문을 확인한다.

- Double Wishbone과 MacPherson이 단순화된 휠 이동 계산이 아니라 각 기구의 구속조건을 실제로 만족하는가?
- 스프링·댐퍼 장착점, 길이, 축, 힘, 반작용이 기계적으로 일관되는가?
- `Car`, `Wheel`, `Suspension`, 기하 솔버, 조향, 타이어의 책임이 중복·충돌 없이 분리되어 있는가?
- 휠 지면 접촉을 교체 가능한 경계로 질의할 수 있으며, `Wheel`이 하나의 접촉 알고리즘에 종속되지 않는가?
- 롤·피치, 공중 주행, 접촉 상실, 전복 상황에서도 통합된 차량이 일관되게 동작하는가?

## 작업 규칙

1. **구현 수정 전에 감사한다.** 5단계는 읽기 전용이다. 코드, 문서, 테스트, 진단, 런타임 근거를 조사하며 이 단계에서 리팩터링하지 않는다.
2. **데이터와 힘의 흐름을 끝까지 추적한다.** 주요 값의 출처, 좌표계, 소유자, 소비자, 갱신 순서를 기록한다.
3. **구현 상태와 검증 상태를 분리한다.** 클래스나 함수가 있다는 사실은 올바른 동작의 증거가 아니다.
4. **시각적 추측보다 근거를 사용한다.** 소스 추적, 독립적인 기하 불변조건, 집중 진단, 테스트, 최신 런타임 확인을 우선한다.
5. **기존 작업 이력을 조용히 다시 쓰지 않는다.** 기존 `1-1`부터 `4-2`까지의 이력을 유지한다. 기존 완료 주장이 근거 부족으로 드러나면 감사 결과에 기록하고, 범위를 합의한 뒤 기존 문서를 명시적으로 수정한다.
6. **각 구현 작업 전에 범위를 합의한다.** 목표, 수정 허용 파일, 제외 파일, 기대 결과, 검증 명령·테스트를 명시한다.
7. **해결 기록을 최신 상태로 유지한다.** 각 단계가 끝날 때 조사 결과, 근거, 합의된 해결책, 영향 파일, 검증 결과, 미해결 질문을 `WheelSuspensionRecoveryPlan.solution.ko.md`와 영문판에 기록한다.
8. **최신 근거 없이 완료를 선언하지 않는다.** 빌드 성공, 테스트 성공, 물리적 정확성은 서로 다른 주장이다.

## 상태 분류

각 요구사항은 구현 상태와 검증 상태를 별도로 기록한다.

### 구현 상태

- **구현됨** — 소스와 데이터 흐름이 요구사항을 충족하는 것으로 보임.
- **부분 구현** — 일부 동작은 있지만 중요한 부분이 누락됨.
- **잘못 연결됨** — 코드가 존재하지만 책임, 좌표계, 갱신 순서, 데이터·힘의 흐름이 설계와 충돌함.
- **미구현** — 요구사항을 구현한 코드를 찾지 못함.
- **미확인** — 관련 구현이나 호출 경로를 아직 찾지 못함.

### 검증 상태

- **검증됨** — 적절한 최신 근거가 해당 불변조건을 직접 뒷받침함.
- **실패** — 재현 가능한 검사 결과가 요구사항과 모순됨.
- **미검증** — 근거가 없거나 오래되었거나 간접적이거나 충분하지 않음.

두 상태를 하나로 합치지 않는다. 예를 들어 접촉 공급자 인터페이스가 구현되어 있어도 접촉점 정확성은 미검증일 수 있다.

# 5단계 — 구현 감사

**목표:** 현재 존재하는 것, 연결 방식, 아키텍처와의 차이를 근거와 함께 파악한다.

**구현 변경:** 5단계에서는 수정하지 않는다.

## 5.1 요구사항 추적

- [ ] 기존 아키텍처 문서의 요구사항과 완료 주장, 특히 `1-1`부터 `4-2`까지를 추출한다.
- [ ] 각 요구사항을 실제 파일·클래스·함수·호출 위치와 연결한다.
- [ ] 체크 표시를 증거로 간주하지 말고 실제로 확인한다.
- [ ] 구현 상태와 검증 상태를 별도로 기록한다.
- [ ] 기존 번호를 유지하고 과거 작업과 이 후속 작업 흐름을 명확히 구분한다.

**산출물:** 근거와 누락 사항이 포함된 요구사항-코드 추적표.

## 5.2 기구학·기계적 정확성

- [ ] Double Wishbone과 MacPherson의 구체 구현 및 모든 런타임 호출 지점을 찾는다.
- [ ] 피벗, 링크·조인트 위치, 스트럿 장착점, 허브 오프셋, 조향축 데이터와 좌표계를 추적한다.
- [ ] 각 솔버가 의도된 고정 길이·조인트 구속조건을 만족하는지 확인한다.
- [ ] 허브 위치·방향이 계산된 기하에서 파생되는지, 단순화된 보정으로 일부 대체되는지 확인한다.
- [ ] 범프·리바운드 한계, 솔버 실패·대체 경로, 연속성, 좌우 대칭, 가능한 스트로크 계산을 검사한다.
- [ ] 고정된 월드 하향 벡터, 차체 로컬 수직 오프셋 등 서스펜션 구속조건을 우회하는 휠 이동 계산을 찾는다.
- [ ] 설정 타입이나 선언만 보고 MacPherson이 구현·사용된 것으로 판단하지 말고, 독립 구현과 런타임 연결을 확인한다.

**산출물:** 각 기구의 구속조건·런타임 사용 여부 평가와 위반 사항 또는 근거 부족 목록.

## 5.3 스프링·댐퍼 및 힘 전달 경로

- [ ] 기하 설정에서 월드 공간 장착점까지의 데이터 흐름을 추적한다.
- [ ] 스프링 길이와 축이 실제 두 장착점에서 계산되는지 확인한다.
- [ ] 압축량, 압축 속도, 스프링 힘, 압축·리바운드 댐핑, 스트로크 한계를 추적한다.
- [ ] 힘이 적용되는 위치와 방향, 반작용이 표현되는 방식을 추적한다.
- [ ] 의도한 기계적 어셈블리를 통해 힘이 전달되는지, 단순화된 우회 경로로 직접 적용되는지 판단한다.
- [ ] 접지, 공중, 완전 압축, 완전 신장, 전복 상태에서 인위적인 끌어당김이나 잘못된 힘 방향이 생기는지 확인한다.
- [ ] 진단 코드가 고정 수직축 같은 오래된 가정을 사용하는지 확인한다.

**산출물:** 장착점 기하에서 힘 계산과 차체 반응까지의 흐름도 및 불일치 목록.

## 5.4 책임과 데이터 소유권

- [ ] `Car`, `Wheel`, `Suspension`, 각 기하 솔버, 조향, 타이어, 접촉 질의 코드의 책임을 조사한다.
- [ ] 허브 위치·방향, 스트로크, 스프링 장착점, 접촉 상태, 휠 회전, 타이어 힘 상태의 소유자를 추적한다.
- [ ] 중복 계산, 오래된 상태, 숨겨진 변경, 클래스마다 다르게 계산되는 값을 찾는다.
- [ ] `Wheel`이 구체 서스펜션 구현에 종속되거나 다른 클래스가 담당해야 할 기구학을 수행하는지 확인한다.
- [ ] 컴포넌트 사이에 각자의 책임에 필요한 데이터만 전달되는지 확인한다.
- [ ] 의도된 런타임 갱신 순서를 기록하고 실제 호출 순서와 비교한다.

**산출물:** 책임 매트릭스와 현재 데이터 흐름도.

## 5.5 지면 접촉 경계

- [ ] 접촉 공급자·질의 인터페이스와 모든 구현체를 찾는다.
- [ ] 휠·허브 상태가 질의 입력으로 변환되고 결과가 서스펜션·타이어에 전달되는 경로를 추적한다.
- [ ] 접촉 위치, 법선, 거리, 유효성의 의미와 좌표계를 확인한다.
- [ ] 미검출, 복수 후보 접촉, 지형·도로 경계, 유효하지 않은 법선의 처리를 확인한다.
- [ ] `Wheel` 수정 없이 다른 알고리즘으로 교체하거나 여러 질의를 결합할 수 있는지 확인한다.
- [ ] API 교체 가능성과 실제 접촉 알고리즘의 물리적 정확성을 구분한다.

**산출물:** 접촉 질의 호출 그래프, 데이터 계약, 결합도·정확성 조사 결과.

## 5.6 차량 런타임 통합

- [ ] 차체 상태부터 기하, 조향, 허브, 접촉, 서스펜션, 타이어 힘, 힘 적용, 강체 적분까지 실제 순서를 추적한다.
- [ ] `Car.cpp/.h`, `Wheel.cpp/.h`, `Suspension.cpp/.h`, 기하 클래스, 타이어 코드, 설정, 관련 진단을 조사한다.
- [ ] 조향 부호와 조향축 사용이 문서의 차량 로컬 좌표계(전방 +Z, 위 +Y, 오른쪽 -X, 왼쪽 +X)에 부합하는지 확인한다.
- [ ] 새 기하 결과를 덮어쓰거나 중복 계산하거나 모순되는 기존 경로를 찾는다.
- [ ] 설정값이 런타임에 전달되는 과정과 기본값·대체 경로를 확인한다.
- [ ] 이상한 시각적 결과를 무조건 렌더링 문제로, 주행 문제를 무조건 물리 문제로 단정하지 말고 텔레메트리와 소스 근거를 대조한다.

**산출물:** 런타임 호출 순서와 우선순위가 매겨진 통합 결함 목록.

## 5.7 검증 수단 조사

- [ ] 빌드 대상, 단위 테스트, 물리·차량 진단, 로그, 재현 가능한 런타임 시나리오를 조사한다.
- [ ] 기하 불변조건을 독립적으로 검사하는 테스트와 구현의 가정을 그대로 반복하는 테스트를 구분한다.
- [ ] 명령어, 기대 불변조건, 출력, 종료 코드, 검사한 리비전을 기록한다.
- [ ] 대칭성, 구속조건 오차, 연속성, 힘 방향, 공중 주행, 접촉 상실, 전복, 스트로크 중 조향 테스트의 누락을 찾는다.
- [ ] 컴파일 성공만으로 물리적 정확성을 주장하지 않는다.

**산출물:** 입증됨·실패함·미검증 상태를 보여주는 검증 매트릭스.

## 5단계 종료 조건

- [ ] 기존 `1-1`부터 `4-2`까지의 모든 요구사항에 판정이 기록되거나, 미확인 사유가 명시되어 있다.
- [ ] 주요 기계적·통합 문제에 소스 위치, 진단, 테스트 또는 명확하게 표시된 근거 부족이 연결되어 있다.
- [ ] 물리적 정확성, 아키텍처 영향, 선행 의존성을 기준으로 조사 결과의 우선순위가 정해져 있다.
- [ ] 감사 중 구현을 수정하지 않았다.
- [ ] 사용자가 조사 결과와 수정 순서를 검토하고 합의했다.

# 6단계 — 올바른 기구학 모델

**목표:** 각 서스펜션 기하가 사용 가능한 스트로크 범위에서 기계적 구속조건을 만족하는 허브 운동을 결정하게 한다.

- [ ] 5단계 조사 결과를 범위가 명확한 작업 단위로 나눈다.
- [ ] 근거가 확인된 Double Wishbone 솔버·구속조건 문제를 수정한다.
- [ ] 근거가 확인된 MacPherson 솔버·구속조건 문제를 수정한다.
- [ ] 스트로크 한계와 불가능한 상태를 명시하고 물리적으로 불가능한 상태를 만드는 조용한 대체 계산을 피한다.
- [ ] 독립적인 기하 불변조건으로 허브 위치·방향, 캠버, 트랙·휠베이스 변화, 좌우 대칭, 스트로크 연속성을 검증한다.
- [ ] 스프링 장착점이 계산된 기하를 따라가는지 확인한다.
- [ ] 코드 변경 전 각 작업 단위의 파일 범위와 검증 방법을 기록한다.

**종료 조건:** 각 구체 모델이 독립적인 기하 테스트를 통과한다. 솔버 테스트 통과만으로 런타임 통합까지 완료된 것으로 보지 않는다.

# 7단계 — 책임과 인터페이스 경계

**목표:** 상충하는 소유권을 제거하고 컴포넌트가 필요한 물리 데이터만 교환하게 한다.

- [ ] 기하, 허브 상태, 스프링·댐퍼 상태, 접촉 상태, 휠 회전, 타이어 힘의 소유자를 정한다.
- [ ] 기하 솔버가 기구학을 소유하고 `Wheel`이나 `Car`가 중복 계산하지 않도록 한다.
- [ ] 서스펜션 힘 모델이 필요한 장착점·상태를 받아 명시적인 힘 결과를 반환하도록 한다.
- [ ] `Wheel`은 구체 서스펜션 알고리즘을 몰라도 허브·접촉·휠 상태를 사용할 수 있도록 한다.
- [ ] 타이어 힘 계산을 서스펜션 내부 구현과 독립적으로 유지한다.
- [ ] 실제 책임 경계나 교체 요구가 입증되지 않은 추상화를 추가하지 않는다.

**종료 조건:** 문서화한 호출·데이터 흐름 계약이 코드와 일치하며 컴포넌트 경계에서 테스트할 수 있다.

# 8단계 — 교체 가능한 지면 접촉 질의

**목표:** 휠·타이어 로직과 접촉 탐색 알고리즘을 분리하고 안정적인 결과 계약을 정의한다.

- [ ] 좌표계, 접촉 유효성, 접촉점, 법선, 관련 거리·특성 정보를 포함해 입력과 결과의 의미를 정한다.
- [ ] 휠 경로가 고정된 레이캐스트 구현이 아니라 공급자 계약을 사용하도록 한다.
- [ ] 접촉 질의 구현을 휠의 서스펜션·힘 책임 밖에 둔다.
- [ ] 필요하면 조기 범용 프레임워크 없이 대체 알고리즘·복수 질의의 선택 및 결합 방식을 정의한다.
- [ ] 지형, 도로, 경계, 미검출, 잘못된 결과, 접촉 전환 상황을 테스트한다.
- [ ] 접촉 제약이 차체를 인위적으로 끌어당기거나 기구학적 스트로크 한계를 무시하지 않는지 확인한다.

**종료 조건:** 경계에서 접촉 알고리즘을 교체·확장할 수 있고 결과 의미를 독립적으로 검증할 수 있다.

# 9단계 — 차량 런타임 통합

**목표:** 검증된 기하, 스프링·댐퍼, 조향, 접촉, 타이어, 강체 경로를 일관된 갱신 순서로 연결한다.

- [ ] 실제 갱신 순서와 상태 의존성을 문서화한다.
- [ ] 합의한 책임 모델과 충돌하는 오래된·중복 계산을 제거한다.
- [ ] 설정된 조향 기하를 통해 허브가 변환되도록 한다.
- [ ] 서스펜션·타이어 힘이 올바른 위치, 방향, 좌표계를 사용하도록 한다.
- [ ] 접촉 상실, 공중 스트로크, 전복이 잘못된 보정력을 만들지 않도록 한다.
- [ ] 설정과 진단이 새 런타임 모델을 반영하는지 확인한다.
- [ ] 핸들링 파라미터 튜닝 전에 일반 주행과 요철 접촉을 검증한다.

**종료 조건:** 런타임 동작이 컴포넌트 계약과 일치하며 검증된 기하를 덮어쓰는 기존 경로가 남아 있지 않다.

# 10단계 — 검증과 회귀 테스트

**목표:** 독립적인 불변조건과 반복 가능한 시나리오로 통합 시스템을 입증한다.

- [ ] 깨끗한 빌드와 집중 기하 테스트를 실행한다.
- [ ] 힘 방향, 스프링·댐퍼, 접촉 경계 테스트를 실행한다.
- [ ] 대칭성, 범프·리바운드 끝점, 연속성, 구속조건 오차를 검사한다.
- [ ] 차체 롤·피치, 한쪽 휠 들림, 공중 주행, 접촉 상실·복구, 극단적 조향, 전복 시나리오를 실행한다.
- [ ] 조향 방향, 횡하중 이동, 타이어 접촉, 원치 않는 휠 드리프트를 반복 가능한 차량 진단으로 검사한다.
- [ ] 대표적인 지형과 도로 경계에서 테스트한다.
- [ ] 리비전, 명령어, 테스트 출력, 실패, 한계, 남은 물리적 근사치를 기록한다.
- [ ] 최신 근거가 뒷받침하는 경우에만 기존 아키텍처 체크 표시를 갱신하고 복구 계획·해결 기록을 동기화한다.

**종료 조건:** 주장하는 동작마다 최신 근거가 있다. 알려진 근사와 실패는 명시하며 테스트하지 않은 항목은 미검증으로 남긴다.
